RPI means Research, Plan, Implement. QRSPI made questions, design discussion, and structure explicit before implementation. QRSPI+ extends that approach with goals, delivery phases, parallelization, integration, acceptance testing, and replanning. The next slide compares the workflows.

From RPI to QRSPI explains the earlier evolution; QRSPI+ documents the expanded implementation. They are related approaches, not interchangeable names or guarantees of correctness.

Compare both implementations, noting their strengths and remaining gaps. The Relay's validation scripts and shared instructions remained valuable foundations.

Other differences: research is isolated from the desired answer, and production code is blocked until a failing test exists. The safeguard miss proves layered checking still matters.

What's next: QRSPI+ is a heavy, fixed pipeline. The next step is a workflow that evaluates and improves itself, which is hill climbing: make one small change, measure it against a baseline, keep it if results get better, and undo it if they don't. GitHub's Autonomous delivery skill is one example. A strong-reasoning orchestrator delegates outcomes to faster workers, then periodically asks, "Is this organization helping us get better results faster?"

Its loop: observed friction, plausible cause, small workflow change, compare useful progress and quality, then keep, revise, or undo. Change one major variable at a time and compare similar work; a faster easy task does not prove a better process. A change that only adds speed while increasing defects or rework does not count. Remove ceremony that no longer earns its cost; even the fixed pipeline becomes one illustration rather than the universal structure.

The evals are the hard part: a fixed set of representative tasks, a baseline, and outcome measures such as first-pass acceptance, defects, integration rework, and time to a usable result. Small samples support hypotheses, not fleet-wide statistics. This connects to the hard-parts section later in the talk.

The hard parts of agentic engineering

Imprecise instructions.
Unpredictable execution.

English is the programming language now.

An agent workflow is itself a system that has to be engineered: evaluated, limited, connected, and maintained. These problems remain even when the workflow works.

Natural-language instructions are inherently imprecise, and the model running them is non-deterministic. The same prompt can produce different results, and each ambiguity can be interpreted differently on each run.

Pin intent down with precise artifacts: acceptance tests, worked examples, schemas, and scripts. Spoken hook: "When English is the programming language, every ambiguity is a bug you haven't found yet."

Evaluate: decide what a better run means before changing the workflow. Use a fixed set of representative tasks, a baseline, and outcome measures such as validated delivery time, rework, escaped defects, review effort, and cost. Case B filed 15 issues about its own process gaps and turned them into automatic checks in the next release. GitHub describes the same loop for Copilot code review: evaluation against known issues plus production signals.

Limit: agents spend tokens, model requests, time, and money, and can retry or loop without converging. Set budgets per task and per run, cap retries and parallel work, and stop or escalate at the limit. The cost to run the process belongs in the same economics as the cost to run the product. In the Stack Overflow 2026 survey, 38% of respondents said their organizations set limits on AI usage.

Hand off: prose handoffs force the next agent to interpret. Structured artifacts with required sections, task IDs, file lists, and test results can be checked by a script. The Relay passed long written plans forward; Case B added an automatic check that every merge contains exactly the planned tasks after a merge silently dropped a security safeguard.

Teams judge a workflow by a few memorable runs. That can mean keeping a change that made results worse because it feels better, or abandoning a useful one after a single bad run. GitHub's Agentic Engineering System (AES) is a tool-agnostic framework for scaling agent use. Implementation guidance is in GitHub Well-Architected. It is a vendor framework rather than an empirical study; use it to show that these lessons fit one model.

Stocks accumulate over time. Governance covers the unskippable checks, permissions, and usage limits. Shared knowledge covers focused context and structured handoffs: agents can only act on what they can access, so weak knowledge turns into fast, confident mistakes. Customer value is the value of completed work, not the amount of work completed.

Activities move work through the system: define, deliver, detect. They line up with the QRSPI+ blocks of align, execute, and verify and learn. Detect feeds what was learned back into governance and shared knowledge, as Case B did with its own process gaps.

Modes describe how people and agents take part: director sets intent, performer does the work, assessor checks it. They are not job titles, and the same person or agent can move between them depending on risk and what governance allows.

AES's health check: as agent use grows, escaped defect rates should stay flat or fall, and shared knowledge should improve alongside delivery speed. If they diverge, the operating model needs attention. Transition: the modes lead into people and teams, where everyone gets promoted.

Managers design the frequency and type of communication. Too chatty, and agents burn tokens and people lose attention. Too quiet, and work drifts or two agents build the same thing. Send a message when it changes what the recipient will do; otherwise, write it down where they can find it.

Example: the mailbox and handoff skills in dfrysinger/skills. Named agent sessions hand files and messages to each other, even across computers, using addresses like name@machine.
