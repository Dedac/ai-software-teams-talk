QRSPI+ runs a fixed route of up to 12 steps, with a shorter quick-fix route for small changes. It helped ship real features, but the process is heavy, and every step costs time, tokens, and attention. BeamRS, coming up shortly, shows the cost: every change, even a framework version bump, was configured for all twelve steps, and on the smaller changes steps were quietly skipped. The next step keeps the lessons and drops the ceremony that no longer earns its cost.

Reduced complexity: start with the smallest organization the task needs and add steps, agents, or specialists only when evidence says they help. The Autonomous delivery skill is one example: an orchestrator adapts task boundaries, context, and concurrency as it learns, rather than following a fixed pipeline.

Evaluation: changes to the workflow are tested against a baseline of representative tasks, measuring first-pass acceptance, defects, rework, and time to a usable result. This is hill climbing: observe friction, guess a cause, make one small change, compare against similar work, then keep, revise, or undo. Speed that adds defects or rework is not a gain.

Review: people still decide what ships and what counts as done. Independent checks and human review stay; what changes is how much process wraps around them.

The evals are the hard part: a fixed set of representative tasks and a baseline. Small samples support hypotheses, not fleet-wide statistics. Next: how do we prove a change actually helped?

A process change feels better long before anyone shows it is better. Treat the workflow like any other change: test it.

Pick a fixed set of representative tasks from real past work: features, bug fixes, and refactors your team actually shipped. Run them through the current process to set a baseline, then through the changed process. Change one major thing at a time so you know what made the difference.

Agents are non-deterministic, so one run proves little. Run each task several times and compare the spread, not a single best result.

Measure outcomes, not activity: first-pass acceptance, defects found later, integration rework, review effort, time to a usable result, and cost to run. Reject a change that adds speed but increases defects or rework. Small samples support hypotheses, not fleet-wide statistics.

"If you can't show it's better, it's just different." Transition: but tune a process too closely to what is in front of you, and it stops fitting what comes next.

Avoid overfitting

Overfitting the process
to today's problems.

The guard

A process tuned to the problems we have today can fail on the problems we'll have tomorrow. Three ways it happens, each with a guard.

Every incident adds a rule: a miss leads to a new step, check, or instruction, and they pile up. The process grows to fight last quarter's failures and brings back instruction overload. Track what each step catches; retire or merge steps that stop catching anything.

Built around today's model: steps and workarounds compensate for the current model's weaknesses. When models improve, those steps become pure cost, and new weaknesses go unchecked. Re-run the evaluation whenever the model or harness changes, and remove workarounds that no longer earn their place.

Tuned to familiar tasks: every tweak that improves the same handful of tasks can make the process worse at everything else. Borrow the train-and-test split from machine learning: keep a held-out set you only run to confirm a change, never to tune it, and rotate in fresh, live work as the codebase and team change. When replaying past work, start from the commit before the fix, so the agent can't find the answer in history. When a measure becomes the target, it stops being a good measure.

"Build the process for the work you'll have, not just the mistakes you've made." Transition: evaluation tells us whether the process improved; review catches what slips through on each change.

A classic ambiguous sentence: the grammar allows both readings, and only context tells you which one the speaker meant. People resolve this with shared context and by asking. An agent picks a reading, often without saying so, and may pick the other one on the next run.

It gets worse with implied information: what the listener fills in that the words never say. "I saw the man with the telescope" can imply he stole my telescope, or that I already found someone I was looking for. Neither is in the sentence; both come from assumed context. Agents fill those gaps too, confidently.

The same thing happens in instructions. "Only run the tests for files you changed" versus "run the tests only for files you changed": does "only" limit which tests, or whether to run anything else? "Make it faster" does not say faster for whom, by how much, or at what cost. Ask the audience for a prompt they wrote that an agent read the other way.

GitHub's Agentic Engineering System (AES) is a tool-agnostic framework for scaling agent use. Implementation guidance is in GitHub Well-Architected. It is a vendor framework rather than an empirical study; use it to show that these lessons fit one model.

Stocks accumulate over time. Governance covers the unskippable checks, permissions, and usage limits. Shared knowledge covers focused context and structured handoffs: agents can only act on what they can access, so weak knowledge turns into fast, confident mistakes. Customer value is the value of completed work, not the amount of work completed.

Activities move work through the system: define, deliver, detect. They line up with the loop from earlier: goals, adaptive build, then evaluate and review. Detect feeds what was learned back into governance and shared knowledge, as Case Study B did with its own process gaps.

Modes describe how people and agents take part: director sets intent, performer does the work, assessor checks it. They are not job titles, and the same person or agent can move between them depending on risk and what governance allows.

AES's health check: as agent use grows, escaped defect rates should stay flat or fall, and shared knowledge should improve alongside delivery speed. If they diverge, the operating model needs attention. Return to the opening: directing agents changes responsibilities, but accountability stays.
